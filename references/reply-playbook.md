# Reply playbook

The aim of every message: make the trade-off visible and let the client choose. Never accuse, never
lecture about the contract, never apologise for charging. Write in the user's own voice and
language. These are shapes to adapt, not scripts to paste.

## Choose the tone

| Situation | Approach |
|---|---|
| Loyal client, first small extra | Do it as a named favour. Log it as `free`. |
| Any client, clear extra of real size | Quote it: what's involved, price, timeline impact, choice. |
| Short, transactional job | Be direct: name the number in one line. |
| Long project with many small extras piling up | Regroup: list what's included vs. new, total it, ask which to keep. |
| Grey area | One specific question. No price unless the user wants one on record. |
| Revision cap reached | Name the round number factually, offer the next round's price or locking the current version. |
| Client pushes back on a fair quote | Restate the choice calmly; offer a smaller version or a later phase. Don't argue the clause twice. |

## Shapes

### Change request (extra work)
> Happy to do [request]! It's outside what we agreed for this project ([short reason, e.g. "the
> package covers 3 concepts"]), so here's what it would take:
> - Work: [what's involved]
> - Cost: [price]
> - Timeline: [+X days / delivery moves to DATE]
>
> Just reply "go ahead" and I'll add it, or we can stick to the original plan. Either is fine with me.

### Several items at once
> Thanks for the notes! Quick breakdown so we're on the same page:
> - Included, doing these now: [list]
> - Extras: [item: price], [item: price]. Total [price], about [+X days]
> - One question: [grey-area question]
>
> Let me know which extras you'd like and I'll update the schedule.

### Courtesy favour (still sets the boundary)
> Done! Happy to include this one at no charge. It's outside our original scope, so just
> flagging it for the future.

### Grey area
> Quick check before I start: [request] isn't covered in our proposal either way. Did you see it
> as part of [deliverable], or as an addition? If it's an addition, it'd be about [price].

### Revision cap reached
> We've now done the [2] rounds included, so these notes would be round [3]. Glad to do it:
> extra rounds are [price] each and add about [X days]. Or, if you're happy with the current
> version, we can lock it as final.

### Regroup when extras have piled up
> A few additions have come in since we started. Each is small, but together they've grown the
> project beyond the original scope. To keep us on time and on budget, here's where we are:
> - Original scope, still on track: [list]
> - New items so far: [list], worth [total]
>
> Which of these would you like to keep? I'll send an updated quote and timeline for those, and the
> rest can wait for a later phase.

### Reversing an approved decision
> Totally possible. Since we locked [stage] on [date] and built on top of it, changing it now
> means redoing [what]. That's about [price] and [+X days]. Want me to go ahead, or keep the
> approved version?

## Things to avoid
- "As per the contract…" openers. Lead with helpfulness, cite only if asked.
- Long justifications. One reason, one number, one choice.
- Asking permission to charge ("would it be okay if I maybe charged…").
- Charging for grey areas without asking first.
- Mixing the price into a paragraph. Put it on its own line.
